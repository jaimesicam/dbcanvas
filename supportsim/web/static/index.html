Vector Lab: learn it by poking it

Seven short steps, from "what is an embedding?" to the exact $vectorSearchSQL you would put in your own app. Everything here runs live, against this clusterdatabase.

1

A sentence becomes 384 numbers

An embedding model reads text and outputs a fixed-length list of numbers, a vector. This app runs all-MiniLM-L6-v2 inside its own process: no API call, no GPU. Every ticket, every article and every query goes through it.

2

Similar meaning → nearby vectors

Cosine similarity measures the angle between two vectors: 1 means they point the same way, 0 means unrelated. Because the vectors are unit length, it is just the sum of 384 products, a[i]×b[i]. Try the presets, especially the last two.

3

The map: every ticket, squashed from 384 dimensions to 2

Each dot is a ticket (◆ = KB article), colored by the team that owns the problem. Nobody told the model about teams. The clusters appear because tickets about the same problem mean similar things. Type something to see where it lands and which tickets are truly nearest. The lines are the real 384-D neighbors, which a 2-D picture can only approximate.

4

Index it

Vectors live in an ordinary field (embedding, an array of 384 doubles). To search them fast you create a vector search index. mongod only records the index; mongot builds and serves it. Note the filter fields: $vectorSearch can only pre-filter on fields declared here.

Vectors live in an ordinary column of pgvector's type, embedding vector(384), next to every other column of the row. To search them fast you create an index like any other, USING hnsw, naming the operator class that matches the distance you will query with: vector_cosine_ops for <=>. An index on one operator is ignored by a query using another. The keyword side is ordinary PostgreSQL: a generated tsvector column and a GIN index.

5

Query it: build a $vectorSearch

numCandidates is how many nearest neighbors the HNSW graph explores before picking the top limit. More candidates means better recall but more work. exact: true skips the graph and scans every vector: perfect recall, linear cost. Recall here is measured against mongot's own exact search.

Query it: ORDER BY embedding <=> $1 LIMIT k

A vector search in PostgreSQL is an ordinary SELECT: order by the distance to the query vector, take the first k. The HNSW index serves that ORDER BY. hnsw.ef_search (default 40) is how many candidates the graph walk keeps: more means better recall and more work. exact turns index scans off, so every row's distance is computed and sorted: perfect recall, linear cost. Filters are plain WHERE clauses on any column, no declaration needed. Recall is measured against that exact query.

6

Fresh off the change stream

mongot keeps its index current by tailing the replica set's change stream. A new document is findable by $vectorSearch a moment after the insert is acknowledged. This inserts a probe ticket and times that moment.

Transactional, not eventual

An HNSW index is updated inside the same transaction as the INSERT, like a B-tree. So a vector search follows the ordinary rules of MVCC: the writing session sees its own row before it commits, other sessions don't, and everyone does the moment it commits. This inserts a probe ticket and asks at each of those three points.

7

Things worth knowing before you build one

One model, both sides. Queries must be embedded with the same model as the documents. Vectors from different models live in different spaces; their cosines are meaningless.
numDimensions must match. MiniLM gives 384. A 1536-wide index will not find 384-wide vectors.
Scores are rescaled. For a cosine index vectorSearchScore = (1 + cos) / 2, so 0.5 means unrelated, not "half similar".
Negation is weak. "I can log in" and "I can't log in" are close (see step 2). Embeddings capture topic better than logic. Pair them with filters or a reranker when it matters.
Pre-filter fields go in the index. filter: {team: "Billing"} only works if team is declared type: "filter".
numCandidates ≈ 10–20 × limit is a good start. Then measure recall like step 5 does.
Search is eventually consistent. Read-your-own-write with $vectorSearch may miss a document for a few milliseconds (step 6).
Vectors cost space. 384 doubles are about 3 KB per document. Store them as BSON binData vectors (float32 / int8) to cut that by 2–8×.
One mongot per replica set. Here it runs on the first member; if that host stops, $vectorSearch fails while ordinary queries keep working.
A missing index returns nothing, not an error. $vectorSearch naming an index that doesn't exist (dropped, misspelled, not built yet) returns 0 results, which looks just like "no matches". Index Workshop step 2 shows it.
int8 vectors need an int8 query. Against a BinData int8 field, a float queryVector silently returns nothing. Quantize the query the same way as the documents.
Search indexes aren't backed up. Backups contain the data (and the vectors); mongot rebuilds its indexes after a restore.
One model, both sides. Queries must be embedded with the same model as the rows. Vectors from different models live in different spaces; their distances are meaningless.
The column fixes the width. vector(384) refuses a 1536-number vector with an error, which is better than silently finding nothing.
Operators are distances, not scores. <=> is cosine distance (0 = same direction), <-> L2 distance, <#> the negative inner product. ORDER BY ascending; 1 - (a <=> b) gives the cosine similarity back.
The operator must match the index. An index built with vector_cosine_ops serves <=> only. Query with <-> and the planner quietly falls back to a sequential scan: right answers, slowly. EXPLAIN tells you (Index Workshop step 3).
ef_search caps the rows. An HNSW scan returns at most hnsw.ef_search rows (default 40). LIMIT 100 with the default returns 40, without an error. Raise it per query with SET LOCAL inside a transaction.
Filters are applied after the index. WHERE team = 'Billing' filters the candidates HNSW returns, so a selective filter can come back short. pgvector 0.8's hnsw.iterative_scan keeps searching; before 0.8, use a partial index per value or a bigger ef_search (Index Workshop step 2).
Small tables are scanned. Under a few thousand rows the planner often picks a sequential scan over the HNSW index, because it is cheaper. That is correct, not a bug; the index takes over as the table grows.
Build memory matters. HNSW builds fast while the graph fits in maintenance_work_mem, and much slower once it doesn't (a NOTICE says so). max_parallel_maintenance_workers parallelises the build.
Vectors are big rows. 384 floats are 1.5 KB per row, close to the TOAST threshold. halfvec halves that; binary_quantize indexes 48 bytes and re-ranks with the full vector (Index Workshop step 1).
Indexes are part of the database. They are WAL-logged, replicated to standbys, and in every physical backup. A replica can serve vector reads; no separate service has to be rebuilt after a restore.
CREATE EXTENSION vector, once per database. The package puts the library on the server; each database still needs the extension created. The Percona Operator does it for you when pgvector is enabled.
Negation is weak. "I can log in" and "I can't log in" are close (see step 2). Pair similarity with filters or a reranker when it matters.

Index Workshop: the choices you make when you define a vector index

Similarity function, quantization, how the vector is stored, whether it is normalized: each is one line in an index definition, and each changes size, speed or correctness. Here they are measured on real indexes, on a copy of the tickets (vector_variants), so the desk is never affected.

Index type (HNSW or IVFFlat), operator class, graph parameters, column type (vector, halfvec, bit), whether the vectors are normalized: each is one clause in a CREATE INDEX, and each changes size, build time, speed or correctness. Here they are measured on real indexes over copies of the tickets (tables vv_* in the supportsim schema), so the desk is never affected.

3

Explain: what did HNSW actually do?

explain("executionStats") on a $vectorSearch returns mongot's own report: which Lucene query ran, how many vectors each segment visited, and how long it took. Compare approximate with exact, small with large numCandidates, and with or without a filter.

EXPLAIN ANALYZE: did it use the index?

The planner decides, per query, whether the vector index is worth it. EXPLAIN (ANALYZE, BUFFERS) shows its choice: an Index Scan on the HNSW index, or a Seq Scan and a Sort. Try the desk's own table (small, so usually scanned), then the variants: the unindexed baseline, IVFFlat with more probes, the binary index's two-step plan, a selective filter.
